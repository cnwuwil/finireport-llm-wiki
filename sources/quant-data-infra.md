# 量化第一课：数据从哪来、怎么存？

## 开篇

没有数据，因子、回测、实盘都无从谈起。但数据从哪接、用什么频率、存成什么样，很多人一开始是懵的。这篇把行情与基础数据的来源、频率、存储选型讲清楚，并加上业内实际用得多的做法，方便你对照和选型。

## 一、数据从哪来：行情源与因子数据源

**交易所直连 / Level-2**：延迟最低、数据最全，但要有席位和运维能力，一般是规模较大的私募或券商在用。

**第三方数据商**：Wind、东方财富、聚宽、米筐、Tushare 等。提供股票/期货的日线、分钟线、tick（部分），以及基本面、指数成分等。私募研究阶段用 Wind、聚宽的很常见；实盘行情往往再用券商或交易所源做校验。

**开源 / 免费**：如 Tushare、AkShare，适合学习和小规模回测，实盘前要核对数据质量和延迟。

业内常见做法：
- 研究阶段：多数私募用 Wind 或聚宽取日线、分钟线、基本面、指数成分；部分会用米筐做回测（接口友好、因子库全）。日频多因子策略通常先把「日频数据 + 因子表」打牢，再考虑分钟/tick。
- 实盘行情：实盘下单前会用券商柜台或交易所行情再对一遍，避免第三方延迟或断线导致信号与成交价偏离；有的机构是「Wind 做研究 + 券商 Level-2 做实盘」双源。
- 成本与取舍：小团队常见组合是「聚宽/米筐 回测 + 券商实盘行情」；上规模后会买 Wind、甚至交易所 Level-2，并自建数据清洗与存储。

## 二、按频率区分：tick、分钟、日频

| 频率 | 典型用途 | 存储要求 |
|------|----------|----------|
| tick | 高频、微观结构、执行 | 时序库、按合约/日分区 |
| 1/5/15分钟 | 中频因子、回测、风控 | 时序或列存，按日/月 |
| 日频 | 多因子、组合、风控归因 | 关系型或列存即可 |

实际用得多的方式：
- 指增/多因子：绝大多数产品以日频为主——日线行情 + 日频因子 + 日频或周频调仓；分钟线多用于「执行分析」或部分中频因子，不会一上来就全上 tick。
- 存储选型：日频因子和组合权重常用 MySQL/PostgreSQL 存；行情和分钟/tick 用 ClickHouse、DolphinDB、QuestDB 等时序/列存，按「日期 + 标的」分区，便于按区间回测和查询。

## 三、怎么存：数据库与存储选型

**关系型（MySQL/PostgreSQL）**：适合日频因子、组合权重、配置表等「结构化、强一致」的数据。

**时序/列存（ClickHouse、QuestDB、DolphinDB）**：适合行情、分钟线、tick。按时间+标的分区，压缩比高、按区间查询快。

**对象存储（S3/OSS）+ Parquet**：冷数据、历史全量行情和因子，成本低，用 Spark/Pandas 按需读。

业内常见做法：
- 热数据：最近 1～2 年日频行情和因子放 MySQL 或 ClickHouse，供回测和实盘信号计算在线查。
- 温数据：更早历史或分钟级数据用分区表 + 按需加载，避免单机内存爆掉。
- 冷数据：3～5 年以上放 OSS + Parquet，需要时用 Spark 或 Pandas 读一段，很多机构用这一套做长期回测和合规留档。

## 四、实战要点

- **统一时间戳**：全用交易所时间或统一用 UTC，避免「自然日 vs 交易日」「Bar 时间 vs 收到时间」混用导致前视或错位。
- **复权与合约**：股票用前复权还是后复权要统一；期货换月、指数成分变更要有版本表，回测才可复现。
- **数据版本**：因子和行情最好带「生成时间/版本号」，便于回测时用「当时可得」的数据，避免前视偏差。

## 五、小结

1. 行情来源：交易所/Level-2 延迟最低，第三方（Wind/聚宽等）做研究和补充；按需求选 tick / 分钟 / 日频。
2. 存储：日频/配置用关系型；行情、分钟/tick 用时序或列存（如 ClickHouse、DolphinDB）；冷数据用对象存储+列式格式。
3. 时间戳、复权、合约与数据版本要统一规范，否则回测和实盘容易对不上。
